# P3.1 — Mô hình và hợp đồng biểu mẫu

Ngày triển khai: 04/11/2026. Phạm vi: mô hình, cấu trúc schema/UI schema, tạo danh mục kèm draft đầu tiên và đọc version. Tái sử dụng bảng `business.form_definitions`, `business.form_versions` đã có; JSONB, FK, unique key/version và revision dùng schema dev/test hiện hữu. Không thêm bảng song song hoặc migration; production vẫn `ddl-auto=none`.

## 1. Hợp đồng schema v1

`schema` dùng tập con JSON Schema 2020-12 với `$schema` bằng `https://json-schema.org/draft/2020-12/schema`, `x-bpm-dialect: bpm-form-v1`. Root bắt buộc có `type: object`, `additionalProperties: false`, `properties` (1–100 trường), `required` (cho phép rỗng). `title` tùy chọn. Chỉ hỗ trợ các thuộc tính được liệt kê dưới đây; thuộc tính lạ bị từ chối thay vì bị bỏ qua. Đây là validator cấu trúc cấu hình nội bộ, chưa phải validator dữ liệu hồ sơ của P3.2 và chưa chọn dependency JSON Schema tổng quát.

Mỗi trường có `title`, `type`, `x-field-type`; `description` tùy chọn. Field ID là key trong `properties`, khớp `[a-z][A-Za-z0-9_]{0,63}`. Nhãn đổi không đổi ID. Builder cần tạo ID một lần khi thêm trường; P3.4/P3.5 kiểm tra tham chiếu khi sửa/version mới.

| x-field-type | type JSON của dữ liệu | Cấu hình được hỗ trợ thêm |
| --- | --- | --- |
| SHORT_TEXT, LONG_TEXT | string | minLength/maxLength nguyên không âm |
| INTEGER | integer | minimum/maximum nguyên trong miền ±9007199254740991 |
| DECIMAL | string | pattern cố định `^-?(0\|[1-9][0-9]*)(\.[0-9]+)?$` |
| MONEY_VND | string | pattern cố định `^(0\|[1-9][0-9]*)$`; VND không âm, nguyên đồng |
| DATE | string | format bắt buộc `date`; giá trị `YYYY-MM-DD`, ngày lịch không timezone |
| SINGLE_SELECT | string | enum gồm 1–100 chuỗi không rỗng, không trùng |
| MULTI_SELECT | array of string | items `{type: string, enum: [...]}`, uniqueItems bắt buộc true, minItems/maxItems tùy chọn |
| CHECKBOX | boolean | Giá trị true/false; false khác với thiếu trường |
| ATTACHMENT | array of UUID string | items `{type: string, format: uuid}`, uniqueItems true, maxItems bắt buộc ≤10, minItems tùy chọn |

Giới hạn min/max phải nhất quán. `title`, `description`, nhãn nhóm và option tối đa 2000 ký tự. Không hỗ trợ `$ref`, schema lồng object, expression, formula, remote enum, nullable hoặc default trong v1. Chuỗi số không có dấu phân cách hàng nghìn, dấu cộng hoặc ký hiệu khoa học. Backend xử lý DECIMAL/MONEY_VND bằng BigDecimal/BigInteger, frontend giữ string; tuyệt đối không chuyển tiền qua JavaScript Number. INTEGER chỉ dùng miền nguyên an toàn JavaScript. Giá trị thiếu biểu diễn bằng việc bỏ key; không dùng null. Kiểm tra payload, ngày lịch, miền số và quyền attachment sẽ thực hiện tại P3.2/P5/P6.

Attachment chỉ lưu ID metadata ứng dụng, không chứa URL/path, tên file hay nội dung Base64. Giới hạn 10 tệp trên toàn hồ sơ là quy tắc nghiệp vụ chung cần áp dụng khi xử lý dữ liệu; maxItems mỗi trường chưa đủ để bảo đảm tổng này.

`required` đánh dấu trường bắt buộc trong định nghĩa dữ liệu. P3.2 phải áp dụng cùng ngữ cảnh action/bước: nháp được thiếu; submit/complete xét tập trường được giao ở ngữ cảnh hiện tại; reject/request changes kiểm tra lý do theo action. Ví dụ submit requester không yêu cầu điền nhóm kế toán hoặc mua hàng.

## 2. UI schema và quyền trường

`uiSchema` chỉ gồm `version: 1` và `groups: [{id, label, fields: [fieldId, ...]}]`. Thứ tự mảng là thứ tự render; mỗi field phải xuất hiện đúng một lần, mỗi nhóm không rỗng và ID nhóm không trùng. Tham chiếu field bị xóa hoặc field thiếu vị trí render bị từ chối.

Không lưu HIDDEN/READ_ONLY/EDITABLE, quyền theo role/action hoặc điều kiện theo bước trong schema/UI schema. Các thuộc tính đó bị từ chối trong cấu hình form. Nguồn quyền duy nhất là step config được pin theo process version (P4); P3.2/P3.6 nhận ngữ cảnh đã được backend phân giải. Người tạo, phòng ban, trạng thái và lịch sử là metadata hệ thống riêng, không phải field cho caller tự ghi.

## 3. DTO và API

API dùng response envelope P1.3 và JWT hiện tại. Cả hai endpoint yêu cầu `form.design`, kiểm tra cả tại controller và use case. Theo mô hình một Admin C-06/C-09, permission này cấp quyền thiết kế toàn bộ danh mục; owner là người tạo, chưa phải scope chia sẻ riêng. Endpoint phục vụ requester/task/binding có policy riêng ở các bước sau.

| Method/path | Request/kết quả |
| --- | --- |
| POST `/api/v1/form-definitions` | `{key, name, description?, schema, uiSchema}` → `{definition, version}` với versionNumber=1, status=DRAFT |
| GET `/api/v1/form-definitions/{definitionId}/versions/{versionId}` | Đọc chính xác cặp definition/version → `{definition, version}` |

`key` khớp `[a-z][a-z0-9_-]{0,99}`, duy nhất toàn hệ thống; name không rỗng, tối đa 200; description tối đa 4000. Server gán UUID, owner/createdBy từ actor, status, versionNumber và revision. Client không chọn owner hay trạng thái. Tạo definition + version + `FORM_CREATED` audit trong cùng transaction. POST trả HTTP 200 theo convention hiện tại, key trùng trả 409 `REVISION_CONFLICT`; retry POST cùng key không tạo thêm version. Cấu hình sai trả 422 `VALIDATION_FAILED` với `details[].field`; metadata sai 400 `INVALID_REQUEST`; chưa đăng nhập 401; thiếu quyền 403; cặp definition/version không tồn tại 404.

`definition`: `{id, key, name, description, ownerUserId, status: ACTIVE|INACTIVE, revision}`.

`version`: `{id, formDefinitionId, versionNumber, status: DRAFT|PUBLISHED|RETIRED, schema, uiSchema, createdBy, publishedBy, publishedAt, revision}`. UUID/Instant truyền bằng string, timestamp ISO-8601 UTC; thông tin publish nullable khi DRAFT. `revision` là khóa lạc quan, tách khỏi business versionNumber. Các JSON snapshot trong DTO là bản sao sâu không sửa được. API save draft/publish/clone và bất biến bản công bố được hoàn thiện P3.5; danh sách/lọc/lịch sử/binding P3.6/P4.

## 4. Form mua sắm và Postman

- Payload tạo form chuẩn: [purchase-request.v1.json](../src/main/resources/forms/purchase-request.v1.json).
- Dữ liệu requester minh họa: [purchase-request.data.json](../src/main/resources/forms/purchase-request.data.json), amount là chuỗi `50000000`.
- Ba nhóm: đề nghị (itemName, quantity, amount, reason, proposalAttachments), ngân sách (budgetCode, budgetConfirmed), thực hiện (completionNote, receivedDate, receiptAttachments).
- Ngưỡng duyệt 50 triệu thuộc cấu hình quy trình được pin, không nhúng vào form như một giới hạn nhập tiền.
- `postman/collections/BPM API/Forms`: Create Form dùng cùng payload mẫu, Get Form Version dùng `formDefinitionId`/`formVersionId` cấp collection. Sau Create, chép hai ID từ `data` vào biến tương ứng. Nếu tạo lại form mẫu, đổi key để tránh conflict. Auth kế thừa collection; không thêm secret.
