# P5.2 — Submit nguyên tử, pin engine version và chống lặp

Ngày 05/11/2026. `POST /api/v1/records/{id}/submit` nhận `{expectedRevision,title,patch:{values,removeFields}}` và header UUID Idempotency-Key. Cần cả record.create/process.start và requester sở hữu record. Quyền gửi độc lập với record.update.draft; server cấp action SUBMIT và quyền nhập tương ứng trong record view, không suy từ UI.

Use case khóa record, đối chiếu receipt actor/key trước state/revision khi retry, kiểm tra owner, DRAFT, revision và startTemplate của đúng process version đã pin. Template khóa definition để serialize với activate/retire. Version phải còn ACTIVE/current PUBLISHED/start-ready, không tự chọn version/schema mới nhất. Validate required của các trường requester được nhập bằng FormAction.SUBMIT; patch HIDDEN/READ_ONLY bị chặn. Snapshot phòng ban chính hiện tại của requester đang ACTIVE từ directory, không nhận department ID từ client.

Data/department được chuẩn bị trong persistence context chung để các hook engine đồng bộ đọc được. Start bằng frozen engineDefinitionId và businessKey server cấp; lưu instance ID, status, submittedAt, department, receipt và RECORD_SUBMITTED audit cùng transaction JPA/Flowable. Lỗi engine sau khi tạo instance, lỗi persistence hoặc audit rollback cả engine/application/receipt. Record identity/process/form pins và instance/department/submittedAt sau submit có guard JPA để tránh thay mapping/về DRAFT do lỗi ghi nội bộ. DB có unique instance mapping; khóa record và state guard bảo đảm một record không start lại bằng key khác.

Receipt dùng unique actor/requestKey và fingerprint typed JSON: bỏ qua thứ tự object/removal fields, giữ kiểu dữ liệu/giá trị/thứ tự array, gồm record ID, revision, title, patch. Retry cùng request trả record hiện tại đã gắn instance, không validate lại startability hoặc tạo audit/instance mới; vẫn kiểm tra quyền hiện tại và requester. Reuse key đổi payload/record trả IDEMPOTENCY_KEY_REUSED. Hai request khác key cùng record chỉ một thắng. Trùng key trên hai record rollback transaction thua, kể cả engine đã start. Không tự retry bằng một key mới khi chưa biết response cũ đã commit hay chưa.

Variables chỉ do backend tạo: bpmRecordId/requesterId/requesterDepartmentId/processVersionId/formVersionId, bpmOutcome=SUBMIT và bpmFormData dưới dạng JSON string. EngineInput giữ giới hạn scalar; không mở arbitrary Java serialization. BpmConditions đọc JSON string (vẫn hỗ trợ map cho artifact/test kỹ thuật cũ), giữ money/decimal string chính xác và dùng compiler expression cố định. Variables không phải API nhận trực tiếp từ client. Nếu BPMN kết thúc đồng bộ trước wait state, status là COMPLETED và có completedAt từ history; còn đang chạy là IN_PROGRESS. Không coi một bước approve là toàn hồ sơ hoàn tất.

Record view chỉ có SUBMIT khi owner có quyền và version hiện còn startable. Nháp retired giữ dữ liệu/quyền lưu nhưng có submitBlockedReason; không tự chuyển schema. Sau submit requester không có save/delete nháp, chỉ xem dữ liệu theo Start policy. Task assignment/inbox/complete được nối tiếp tại P5.3–P5.8.

Frontend dùng renderer validate SUBMIT, gửi revision/payload hiện tại và cache attempt key theo record/revision/title/typed patch. Mất response giữ input và key, retry cùng payload; thay nội dung tạo attempt mới. Thành công hiển thị “Đã gửi hồ sơ” và status thật từ backend, bỏ các nút draft; không báo hoàn tất khi instance còn chạy. New record vẫn lưu draft trước khi gửi, nên luôn có record ID làm ranh giới chống lặp.

Kiểm chứng: full backend HTTP/JWT/PostgreSQL/Flowable, concurrency cùng/khác key, key trùng qua record, payload đổi, required/field/owner/department/startability, snapshot department khi user chuyển phòng, chọn lại business v1 khi engine đã có v2, rollback audit và lỗi ngay sau real engine.start, typed JSON threshold 49.999.999/50.000.000/50.000.001 và synchronous completion. Receipt/revision replay trước retire được kiểm tra lại sau retire. Có thêm submit-only/thu hồi process.start và unit fingerprint/JSON scalar. Frontend chạy toàn bộ form/model/Chrome; smoke test-only server nối designer/publish/clone, draft pinning/retire và submit, làm mất response sau commit rồi retry cùng key. Kết quả cuối ở README/Implementation Plan; không tính restart opt-in chưa chạy/UAT đã đạt.

Postman Submit Record kế thừa auth và dùng recordOperationKey. Request không cập nhật recordRevision sau response để exact retry giữ body cũ; lấy revision mới trước một thao tác mới. Patch rỗng chỉ hợp lệ khi dữ liệu đã lưu đủ required. Runbook smoke ở P4.8, hiện test hỗ trợ cả submit; server chỉ dùng bpm_test và không được chạy đồng thời với suite khác trên cùng DB.
